# Локальная почта и SMTP

## Текущий запуск

В рабочем локальном окружении остаётся `MAIL_TRANSPORT=local`. Письма сохраняются
в `.local/mail`, просмотр — `http://localhost:8025`. Внешний провайдер не подключён,
реальные SMTP-реквизиты не создавались. При ошибке SMTP нет автоматического
переключения на локальные JSON-файлы и ложного подтверждения отправки.

Единая фабрика транспорта обслуживает подтверждение аккаунта, восстановление
пароля, одноразовые коды гостей и worker уведомлений о встречах. `LocalMail` —
сохранённое внутреннее имя общего формата сообщения; SMTP не читает локальную почту
и не отправляет накопленные файлы.

## Подключение после выбора провайдера

В окружении веб-приложения и worker укажите:

```dotenv
APP_URL=https://your-slotly-domain.example
MAIL_TRANSPORT=smtp
SMTP_HOST=smtp.provider.example
SMTP_PORT=587
SMTP_SECURITY=starttls
SMTP_USER=your-smtp-login
SMTP_PASSWORD=your-smtp-password
MAIL_FROM=noreply@your-domain.example
CLIENT_IP_HEADER=x-slotly-proxy-ip
```

Пример содержит только заполнители. Имя SMTP-сервера — DNS hostname без URL,
пути и параметров; `MAIL_FROM` — один email без display-name. Заголовок отправителя
формируется как Slotly. Для TLS с начала соединения используйте `SMTP_SECURITY=tls`
и порт провайдера (обычно 465); для обязательного STARTTLS — `starttls` (обычно 587).
Все SMTP-поля обязательны. Plaintext-режима и выключателя проверки сертификата нет.
Для SMTP требуется HTTPS `APP_URL`, в том числе для ссылок из писем.

Секреты передаются через закрытое окружение или локальный `.env.local`, никогда
через NEXT_PUBLIC, Git, аргументы CLI или административный файл базы данных.
После изменения перезапустите веб-сервер и worker. Проверьте:

```sh
npm run env:check
npm run mail:check
```

`mail:check` выполняет соединение, проверку TLS и аутентификацию; **письмо не
отправляет**. Это не проверка разрешённого MAIL_FROM, попадания во входящие или
доставляемости домена. В локальном режиме команда не делает внешних соединений.
`mail:local` разрешён только для local-режима и loopback-приложения.

## Общие лимиты отправки

В SMTP-режиме web и worker используют общие счётчики PostgreSQL. По умолчанию:
`MAIL_MAX_PER_HOUR=100`, `MAIL_MAX_PER_DAY=1000`,
`MAIL_RECIPIENT_MAX_PER_HOUR=20`, `MAIL_RECIPIENT_MAX_PER_DAY=100`.
Каждый параметр — целое число от 1 до 1 000 000; его нужно согласовать с реальными
квотами провайдера. Это технические настройки сервера, не настройки организатора.

Окно начинается с первого списания и длится час или 24 часа; это не календарные
сутки конкретного часового пояса. Одно разрешение списывает все четыре счётчика
одной транзакцией до SMTP. При отказе одного счётчика остальные не меняются.
Сбой SMTP не возвращает разрешение: после разрыва результат отправки может быть
неизвестен. Недоступные счётчики запрещают отправку. Изменение конфигурации не
обнуляет уже израсходованный бюджет текущего окна.

В таблице `mail_delivery_limits` сохраняются только HMAC-ключи, числа и срок окна;
email, IP и текст писем не сохраняются. Строки, истёкшие больше суток назад,
удаляются порциями по 100 при следующем запросе лимита. Без активности очистки нет.
Письма из локального просмотрщика бюджет не расходуют.

Запросы регистрации, повторного подтверждения и сброса пароля в SMTP-режиме
дополнительно ограничены по нормализованному email: 1 в минуту и 5 в час,
до поиска аккаунта. Превышение даёт HTTP 429 и Retry-After одинаково для известных
и неизвестных адресов. Гостевые запросы сохраняют свои существующие ограничения.
До входа в Better Auth эти же запросы ограничены по IP или IPv6 /64: 10 в минуту
и 60 в час, чтобы смена email не создавала неограниченное количество счётчиков.

Если бюджет закончился уже перед отправкой auth-письма, публичный ответ остаётся
общим, чтобы не раскрывать наличие аккаунта. Письмо не отправляется и не ставится
в очередь; нужно повторить запрос после восстановления бюджета. Аккаунт остаётся
неподтверждённым. У OTP возвращаются 429/Retry-After; запись не подтверждается.
Уведомление встречи остаётся в очереди до нового окна без расхода попыток SMTP,
с `last_error=MAIL_RATE_LIMITED`. `ops:check` показывает число `budgetDeferred`;
обычный контроль возраста очереди продолжает отмечать длительное ожидание.

## Гарантии и ограничения

Nodemailer закреплён в lockfile. TLS обязателен, сертификат и имя сервера проверяются;
минимальная версия TLS 1.2. Логирование SMTP-диалога отключено. Ограничены времена
DNS/соединения/приветствия (5 секунд) и ожидания активности сокета (15 секунд).
Это таймауты стадий, не общий дедлайн операции.

Получатель — один валидный email с фиксированным envelope. Нельзя передать
список адресов через поле получателя, CR/LF в теме, внешнюю ссылку действия, файлы
или URL-вложения. Тело письма — текст; ссылка подтверждения/управления включается
в текст без потери `#token`. Для сообщений очереди сохраняются исходные Date и
Message-ID. Сырые ошибки, контакты, SMTP-пароль и токены не выводятся в CLI-ошибках.
PG-клиенты не наследуют почтовые секреты.

Успешная отправка означает, что SMTP-сервер принял сообщение после DATA. Статус
в очереди не подтверждает доставку во входящие. При разрыве после принятия письма
и до фиксации результата возможен повтор; одинаковый Message-ID не гарантирует
дедупликацию сторонним провайдером. Уведомления используют существующие аренды,
лимит попыток и отложенные повторы; HTTP-ответы подтверждения/OTP сохраняют свои
отдельные правила. Очередь уведомлений не превращается в очередь auth-писем.

Перед публичным пилотом ещё нужны выбранный провайдер, подтверждённый sender,
SPF/DKIM/DMARC, согласованные квоты и лимиты, обработка bounce/complaint/suppression,
согласованные [настройки защиты](abuse-protection.md). Нужно проверить выбранный
заголовок и сетевую изоляцию реального reverse proxy. Затем отдельно
проверяется реальная доставка на согласованные тестовые адреса. Эти работы и
HTTPS-хостинг не включаются автоматически установкой SMTP-библиотеки.

## Проверки

Unit-тесты поднимают временный SMTP-сервер только на loopback и проверяют SMTPS,
STARTTLS, аутентификацию, MIME, ссылки и Message-ID, отказ от недоверенного
сертификата, отсутствие отправки AUTH без TLS, отказ DATA и verify без сообщения.
Сертификат создаётся заново OpenSSL во временном личном каталоге и удаляется после
тестов. На Windows используется OpenSSL из Git for Windows, иначе — из PATH.
Доверие тестов задаётся только дочернему Node-процессу через NODE_EXTRA_CA_CERTS;
системное хранилище и production-проверка TLS не меняются.

Основания: [SMTP transport](https://nodemailer.com/smtp) и
[message configuration](https://nodemailer.com/message).
