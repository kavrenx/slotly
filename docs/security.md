# Доступ к PostgreSQL и защита браузера

## Локальные роли

После `setup`, запуска PostgreSQL и миграций выполните `npm run db:roles`.
Команда работает только с локальной БД вне production; исходному подключению
нужны права администратора. Перед изменением локальных настроек сохраняется
закрытая копия `.env.local` в `.local/access`. Данные таблиц не переписываются.

Создаются два случайных логина со случайными паролями:

- **Приложение**: подключение, чтение и необходимые операции с данными `slotly`.
  Без владения объектами, членства в других ролях, CREATE/TEMP, TRUNCATE, DDL,
  управления ролями, репликации и обхода RLS. Снимки `bookings` и история
  `booking_events` доступны только для чтения и добавления; занятость нельзя удалять.
  Проверки целостности и триггеры продолжают действовать.
- **Миграции**: владелец схем `slotly`/`drizzle` и их объектов, с CREATE в этой БД.
  Без superuser, CREATEDB и CREATEROLE. Может менять схему и ограничения, поэтому
  этот доступ не используется веб-сервером и обработчиком уведомлений.

Администратор сохраняется для запуска локального кластера, тестовых баз,
резервного копирования и восстановления. Его права относятся к кластеру;
это отдельный эксплуатационный доступ, а не роль приложения.

`.env.local` получает только runtime `DATABASE_URL`; ключ копий переносится в
`.env.operations.local`. В этом отдельном файле находятся `ADMIN_DATABASE_URL`,
`MIGRATION_DATABASE_URL`, служебная копия `RUNTIME_DATABASE_URL` и прежний
`BACKUP_ENCRYPTION_KEY`. Он читается только операторскими CLI, не загружается
Next.js и исключён из Git и server tracing. `npm run setup` сохраняет этот ключ.
На Unix файлы создаются с 0600, каталоги — 0700; на Windows важны ACL профиля.

После команды перезапустите веб-сервер и worker. Повторный `db:roles` использует
сохранённые логины, не меняет пароли и повторяет назначение прав. Если выполнение
прервалось после сохранения служебного файла, повторите команду. При ошибке
транзакции SQL-изменения откатываются, настройки приложения не переключаются.

`db:migrate` и Drizzle config выбирают миграционный URL, `db:local`, копии и
интеграционные тесты — административный. Без отдельного URL старый локальный
режим совместимости использует `DATABASE_URL`; `ops:check` отмечает чрезмерные
runtime-права как `RUNTIME_ROLE_PRIVILEGED` и возвращает 2.

## Следующие миграции и восстановление

Новые таблицы и функции **не получают** runtime-доступ автоматически. Default
EXECUTE для PUBLIC также отозван. После миграции администратор должен проверить
новые объекты и явно выдать нужные права. Локально после такой проверки можно
повторить `db:roles`: команда предоставляет DML на текущие таблицы `slotly`, затем
повторно ограничивает снимки и историю. Это не средство ограничения данных между
организаторами: их авторизацию по-прежнему выполняют серверные операции.

Действующие объекты передаются миграционному владельцу адресно, без
`REASSIGN OWNED` для всего кластера. Функции `slotly` получают `search_path=pg_catalog`;
обращения к данным в их теле квалифицированы схемой. PUBLIC не получает доступ
к прикладным схемам; CREATE в `public` отозван в целевой базе.

Дамп `--no-owner --no-acl` не переносит логины и права кластера. Перед переключением
на восстановленную базу назначьте владельца и runtime-права заново. Для новой
локальной базы используйте отдельные настройки её администратора и `db:roles`;
не копируйте URL старой базы без изменения имени. Сохраните служебные настройки
и ключ шифрования отдельно от компьютера и копий.

Для managed PostgreSQL локальный установщик не применяется: имена ролей,
предустановка `btree_gist`, владение и разрешённые административные операции
согласуются с выбранным провайдером. Веб-процессу передаются только runtime URL
и нужные ему прикладные секреты. Административный файл и ключ копий не разворачиваются
вместе с приложением. Автоматического развёртывания и провайдера пока нет.

## Заголовки и CSP

`src/proxy.ts` создаёт новый криптографический nonce на каждом запросе страницы
и API, заменяя одноимённые входящие заголовки. Политика передаётся в запрос рендера
и ответ, чтобы Next.js разрешал собственные скрипты этим nonce. Скрипты без nonce
и обработчики вроде `onclick` в HTML блокируются. В production нет `unsafe-eval`;
в development он нужен инструментам React/Next.js, как и WebSocket для HMR.

Root layout ждёт `connection()`: HTML формируется для запроса, не сохраняется как
общая статическая страница и отдаётся с `private, no-store`. Это осознанная цена
nonce CSP; отдельная оптимизация кеширования возможна позже. Статические файлы
`_next` не проходят через Proxy и сохраняют обычный кеш Next.js.

Разрешены собственные источники, data/blob-изображения и inline-стили: позиционирование
слотов, курсор и 3D-наклон используют style attributes. Это исключение для стилей,
а не скриптов. Запрещены плагины, фреймы, встраивание страницы и изменение base URL;
формы ограничены своим origin. Сохраняются `nosniff`, `no-referrer`, DENY и ограничения
камеры/микрофона/геолокации. При HTTPS `APP_URL` добавляются upgrade-insecure-requests
и HSTS на год, без includeSubDomains/preload; localhost остаётся на HTTP.

Политика исполняется, не только report-only. Внешний сбор CSP-отчётов не подключён.
Интеграционные тесты проверяют бизнес-сценарии с runtime-ролью, отдельные проверки
подтверждают запреты DDL/изменения истории и выдачу прав на будущие объекты.
Браузерная проверка нужна на production-сборке: гидратация, навигация, формы и демо.
`npm run security:check` на запущенной production-сборке проверяет реальные HTTP-ответы
пяти страниц, включая 404, свежие nonce и их наличие на скриптах HTML.
GitHub CI запускает эту проверку после сборки.

Основания: [права PostgreSQL 18](https://www.postgresql.org/docs/18/ddl-priv.html),
[default privileges](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html),
[CSP в Next.js](https://nextjs.org/docs/app/guides/content-security-policy) и документация
установленной версии в `node_modules/next/dist/docs`.
