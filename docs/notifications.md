# Уведомления — этап 8

## Поведение

Новое событие создания, переноса или отмены записи ставит в очередь два письма:
участнику и организатору, включая отмену самим организатором. Письмо содержит
название, участников, место, время с датой, именованным часовым поясом и UTC-смещением,
номер записи и версию события. При переносе показаны оба интервала, при отмене —
отменённый интервал, автор и пояснение. Оба конца интервала форматируются полностью:
корректны переход через полночь и повторный час DST.

Участник получает личную ссылку `/manage#token=...`, организатор — обычную ссылку
на защищённый кабинет. Capability вычисляется непосредственно при отправке;
очередь не хранит токен. Письма содержат предупреждение о приватности ссылки.
Для проверки используйте локальную почту `http://localhost:8025`; внешняя доставка
включается отдельной [SMTP-конфигурацией](mail.md), сейчас она не подключена. Просмотрщик допускает кнопки только на APP_URL
и известные маршруты, экранирует всё содержимое писем.

Старые события при миграции **не рассылаются**. Новые изменения ранее созданных
встреч получают уведомления. Подтверждение аккаунта, восстановление пароля и
одноразовые коды гостей сохраняют отдельную синхронную доставку и собственные
правила повторов: очередь этого этапа отвечает только за события встреч.

## Транзакционная граница

Миграция `0007_notification_outbox.sql` добавляет таблицу и `AFTER INSERT`-триггер
на `booking_events`. Каждое событие создаёт два задания в той же PostgreSQL-транзакции,
включая отложенные ограничения целостности на COMMIT. Нет ситуации «встреча
сохранена, задание потеряно». Ошибка постановки откатывает изменение встречи.
Уникальность `(event_id, audience)` и идемпотентность событий предотвращают дубли.

Адрес получателя, его часовой пояс и имя организатора сохраняются снимком.
Для организатора используется текущий часовой пояс расписания на момент события;
для участника — его сохранённая зона. Изменение профиля после постановки письма
не меняет получателя. Содержимое встречи берётся из неизменяемого `bookings`,
интервалы и пояснение — из неизменяемого события, а не из текущей занятости.
Триггер защищает поля снимка задания от UPDATE. Очередь не является источником
состояния встречи.

## Обработчик и восстановление

Обработчик запускается отдельным Node-процессом вместе с `npm run dev` и
`npm run start`. Он не зависит от посещения страниц, React, таймеров браузера,
`after()` или срока жизни HTTP-запроса. Доступны отдельные команды:

```powershell
npm run notifications:work   # непрерывный обработчик
npm run notifications:once   # до 100 доступных заданий, затем выход
npm run notifications:status # pending / sent / failed, без адресов и токенов
npm run notifications:retry  # явный возврат всех failed в очередь
```

Захват — атомарный `UPDATE` с `FOR UPDATE SKIP LOCKED`, арендой на 120 секунд и
случайным UUID аренды. Несколько процессов безопасно разделяют задания. Запись
результата проверяет UUID: прежний процесс не подтвердит уже перехваченное задание.
Отправка происходит вне транзакции, не удерживает блокировки бронирований.
После аварии аренда истекает и письмо подхватывается снова. Успешные письма
сами не возвращаются в очередь.

Письма одной встречи для одного адресата следуют версиям событий. Ошибка одного
получателя не блокирует другого и другие встречи. До восьми попыток с интервалами
5, 10, 20, 40, 80, 160, 320 секунд; затем `failed`. Истёкшая аренда восьмой попытки
также становится `failed`. Терминальная ошибка не блокирует новые события.
Ручной повтор failed может поэтому доставить старое событие после нового:
письмо всегда указывает номер изменения и предлагает посмотреть актуальную запись.

В БД/журнале сохраняются только контролируемые коды ошибки, без исключений
провайдера, текста писем, адресов и секретов. Команда статуса нужна для диагностики;
автоматического мониторинга публичного сервиса пока нет.

## Гарантии доставки и границы

Очередь обеспечивает повторную обработку (at least once). Локальный транспорт
дополнительно использует стабильные UUID сообщения и время создания задания:
после сбоя между записью файла и подтверждением очереди остаётся один файл.
Публикация файла атомарна; идентичный повтор безопасен, иное содержимое с тем же
ID не перезаписывает письмо. Exactly once для произвольного внешнего SMTP не
обещается. При подключении провайдера нужен его идемпотентный API либо принятие
возможных повторов. Таймаут отправки должен быть меньше аренды.

Ротация `BETTER_AUTH_SECRET` отзывает все личные ссылки, включая уже доставленные
в письмах. При крайне редком сочетании ротации и неподтверждённого локального
файла повтор с новым токеном получит `DELIVERY_FAILED`, сохранив прежний файл:
это требует диагностики, а не скрытого переписывания доставленного сообщения.
Внешний почтовый провайдер, SPF/DKIM/DMARC, работа нескольких хостов, мониторинг
failed, политика хранения/очистки адресов и файлов, напоминания перед встречами и
календарные интеграции — отдельные задачи перед соответствующим запуском.

`run-app.mjs` запускает веб-сервер и обработчик одной командой; остановка или
аварийный выход одного завершает второй. База и просмотрщик почты запускаются
отдельно, как раньше. Миграции выполняются явно до запуска приложения.

## Проверки

Реальный PostgreSQL: атомарность постановки и отката, ошибка enqueue при отмене,
идемпотентный повтор команды, снимки получателей, два часовых пояса, порядок
событий при нескольких обработчиках, невидимость незавершённой транзакции,
backoff, исчерпание попыток, явный повтор, истечение аренды, fencing устаревшего
процесса и сбой после фактической локальной отправки. Модульно проверены переход
через полночь, повторный час DST, стабильность письма и защита заголовков.
